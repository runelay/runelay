Uma alternativa leve ao IBM ContextForge

O Runelay, gateway MCP open source, e o IBM ContextForge colocam servidores MCP atrás de um endpoint. O ContextForge é um gateway e registro para organizações, que junta MCP, A2A e APIs REST ou gRPC; o Runelay é para os agentes de uma pessoa, como app desktop ou um container. Esta página lista o que muda, com as fontes.

O Runelay serve quando

  • São os seus agentes, não a empresa inteira, que precisam de um endpoint MCP.
  • Você quer um app desktop ou um único container, sem PostgreSQL, Redis ou chart do Helm.
  • Os seus agentes devem dividir memória, além de contas e skills.
  • Você já tem servidores MCP nos agentes e quer importar com runelay migrate.

O ContextForge serve quando

  • Você quer servidores virtuais que agrupam as tools escolhidas, e serviços REST ou gRPC expostos como MCP.
  • Muitos usuários trabalham em times, com RBAC e SSO pelo Entra ID, Okta, Keycloak ou outro provedor OIDC.
  • Você precisa de tracing com OpenTelemetry, métricas no Prometheus e um painel de admin com logs ao vivo.
  • Você quer plugins e guardrails, agentes A2A no mesmo gateway e federação entre clusters no Kubernetes.

Perguntas

O Runelay tem relação com o IBM ContextForge?

Não. O Runelay é um projeto MIT separado, escrito com Bun, Hono, SQLite e React. O ContextForge é um projeto Python com licença Apache 2.0 na organização da IBM no GitHub.

Preciso de PostgreSQL e Redis para hospedar um gateway MCP?

Com o Runelay, não: o app desktop roda no seu computador e, no servidor, é um container. O ContextForge roda com SQLite em desenvolvimento e documenta PostgreSQL e Redis para produção.

Dá para sair do ContextForge para o Runelay?

O Runelay aceita qualquer URL de MCP remoto, comando local ou spec OpenAPI, então você adiciona os servidores que usa um a um. O runelay migrate importa o que está configurado nos seus agentes, não os servidores cadastrados no ContextForge.
