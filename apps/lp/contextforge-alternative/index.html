A lightweight IBM ContextForge alternative

Runelay, an open source MCP gateway, and IBM ContextForge both put MCP servers behind one endpoint. ContextForge is a gateway and registry for organizations that federates MCP, A2A and REST or gRPC APIs; Runelay is for one person's agents, as a desktop app or one container. This page lists what differs, with sources.

Runelay fits when

  • It is your own agents, not a whole company, that need one MCP endpoint.
  • You want a desktop app or a single container, without PostgreSQL, Redis or a Helm chart.
  • Your agents should share memory as well as accounts and skills.
  • You already have MCP servers in your agents and want to import them with runelay migrate.

ContextForge fits when

  • You want virtual servers that bundle chosen tools, and REST or gRPC services exposed as MCP.
  • Many users work in teams, with RBAC and SSO through Entra ID, Okta, Keycloak or another OIDC provider.
  • You need OpenTelemetry tracing, Prometheus metrics and an admin UI with a live log viewer.
  • You want plugins and guardrails, A2A agents in the same gateway, and multi-cluster federation on Kubernetes.

Questions

Is Runelay related to IBM ContextForge?

No. Runelay is a separate MIT project written with Bun, Hono, SQLite and React. ContextForge is an Apache 2.0 Python project under the IBM GitHub organization.

Do I need PostgreSQL and Redis to self-host an MCP gateway?

Not with Runelay: the desktop app runs on your computer, and on a server it is one container. ContextForge runs with SQLite in development and documents PostgreSQL and Redis for production.

Can I move from ContextForge to Runelay?

Runelay accepts any remote MCP URL, local command or OpenAPI spec, so you can add the servers you use one by one. runelay migrate imports what is configured in your agents, not the servers registered in ContextForge.
